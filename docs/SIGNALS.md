# Windows signal compatibility

This subsystem delivers only cooperative Windows events, and it is CLI-oriented. It is not a POSIX signal implementation.

Available: pcntl_signal, pcntl_signal_get_handler, pcntl_signal_dispatch, pcntl_sigprocmask, pcntl_alarm, pcntl_sigwaitinfo, pcntl_sigtimedwait and a nonstandard pcntl_windows_raise for testable in-process events. It installs a Windows console control handler to queue CTRL_C as SIGINT and CTRL_BREAK as a SIGTERM-like cooperative event. The console callback never runs PHP code. Registered PHP handlers execute on the PHP thread via pcntl_signal_dispatch or, when pcntl_async_signals(true) is enabled, through a Zend VM interrupt hook. The timer queue callback only queues an event and schedules a VM interrupt.

Known differences: SIGUSR1, SIGUSR2, SIGHUP, SIGQUIT and SIGCONT have no native OS delivery source (they can be sent through pcntl_windows_raise). SIGQUIT is not generated by Ctrl+Break (which continues to queue the extension's SIGTERM-like event), and SIGCONT does not resume a suspended Windows process. SIGCHLD is now enqueued when a registered child exits, using Windows threadpool wait callbacks and a single-delivery guard; this does not notify for arbitrary unrelated processes. Standard POSIX signal masks apply only to extension-owned cooperative events. SIG_DFL does not synthesize Unix signal dispositions for injected events. Restarting interrupted system calls is not supported. pcntl_alarm schedules a Windows timer; handlers are dispatched automatically only with pcntl_async_signals(true), otherwise explicitly via pcntl_signal_dispatch. No POSIX siginfo metadata or process-directed kill is guaranteed.

Do not treat pcntl_windows_raise as posix_kill. The VM interrupt bridge targets one active CLI request per process. Overlapping requests in a ZTS host are **rejected during PHP module request initialization** because the signal queue and VM interrupt target are process-wide. Real POSIX signal delivery and POSIX syscall interruption/restart semantics remain unavailable.

Synchronous signal waits use a Windows kernel event rather than a 1 ms polling loop. An unrelated queued signal cannot consume a signal requested by sigwaitinfo/sigtimedwait; the appropriate signal remains pending until explicitly consumed or dispatched. Synchronous signal waits consume extension-managed pending events only. Timeout handling uses Windows millisecond scheduling and may exceed a requested nanosecond interval. These calls do not receive arbitrary process-directed POSIX kernel signals.

Windows child exit notifications are registered per child handle. They queue SIGCHLD without executing PHP code outside the main thread. Notifications are unregistered before the child record is released. A normal wait can enqueue the notification if a callback has not yet run.

Unblocking queued events schedules a fresh VM interrupt when async dispatch is
enabled. Dispatch has a recursion guard, and events queued inside a handler are
scheduled again after that handler returns. A thrown PHP exception releases the
guard. Output arrays respect PHP typed-reference constraints.

As in current upstream PHP 8.4/8.5, `pcntl_sigtimedwait` requires a positive
total duration, even if a signal is already queued. Use a positive nanosecond
value for a short wait; Windows rounds this to millisecond scheduling. Large
nonnegative seconds are accepted with saturating conversion rather than wrapping
into a short timeout. On timeout the supplied info variable is unchanged.

Callbacks currently receive only the signal number, without an upstream kernel
siginfo argument. Additional argument/error differences are recorded in
[COMPATIBILITY.md](COMPATIBILITY.md).

## Framework signal registration

The native extension provides the signal constants and cooperative handler registration used by Symfony Console (`SIGINT`, `SIGQUIT`, `SIGTERM`, `SIGUSR1`, `SIGUSR2`, `SIGALRM`) and Laravel 13's queue worker (`SIGQUIT`, `SIGTERM`, `SIGINT`, `SIGUSR2`, `SIGCONT`). `SIGQUIT` uses number 3 and `SIGCONT` number 18 in this extension. The focused Windows PHPTs `037-framework-signals.phpt` and `038-framework-signal-mask.phpt` check registration, in-process delivery, masking and asynchronous dispatch.

**This is an API-level framework compatibility improvement, not Unix process-signal parity or a verified Laravel queue worker.** There is no cross-process POSIX signal delivery for SIGQUIT/SIGCONT, and `SIGCONT` does not unstop an OS process. Supervisors must use Windows-appropriate process lifecycle controls. Timeout alarms run through cooperative Zend VM interrupts and cannot guarantee preemption of a blocked Windows native system call. Always run Artisan startup, job execution, timeout, shutdown, and pause/resume tests on the intended PHP build before declaring Laravel worker compatibility.
